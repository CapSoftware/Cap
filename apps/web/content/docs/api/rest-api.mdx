The Cap Developer API lets your product host video with Cap. You upload a file, Cap encodes it, and you play it back as adaptive HLS or MP4, or with the hosted player.

There are two APIs:

- **REST API** (`/api/developer/v1`) -- Server-side: create uploads and manage videos and usage, authenticated with secret keys (`csk_`).
- **SDK API** (`/api/developer/sdk/v1`) -- Browser-side: upload a video's file, authenticated with an upload token (`cut_`) that your server creates for that one video.

These keys do not authenticate the Cap CLI. For CLI keys (`cap_cli_`), used with `CAP_API_KEY` in headless environments, see [Set Up Your Agent](/docs/agents/setup#headless-environments-ci-containers-and-remote-sandboxes).

A video goes through four steps:

1. [Create Upload](/docs/api/rest-api#create-upload) from your server with the secret key. It returns an upload token.
2. Upload the file from the browser with that token, using [Multipart Upload](/docs/api/rest-api#multipart-upload).
3. Poll [Get Video Status](/docs/api/rest-api#get-video-status) with the secret key until `status` is `ready` or `errored`.
4. Play it. See [Play a Video](/docs/api/rest-api#play-a-video).

## Authentication

### Getting Your API Keys

API keys are managed in Cap Infra, not the general Settings page.

1. Go to [cap.so/dashboard/infra](/dashboard/infra).
2. Create an app and give it a name and environment (development or production).
3. Two keys are generated for each app:
   - **Secret key** (`csk_...`) -- Must be kept private. Used with the REST API, including to create uploads.
   - **Public key** (`cpk_...`) -- Cannot create or upload videos. Browsers upload with an upload token instead.
4. Store both keys securely. You can generate a new pair on the API keys page, which revokes the previous pair.

### Using Your Keys

Include the appropriate key in the `Authorization` header as a Bearer token:

```
Authorization: Bearer csk_your_secret_key_here
```

The SDK API takes an upload token instead. Your server gets one from [Create Upload](/docs/api/rest-api#create-upload) and hands it to the browser:

```
Authorization: Bearer cut_your_upload_token_here
```

An upload token works for one video and for a limited time, so it is safe to send to the browser. A public key on its own cannot start an upload: the SDK API answers `403` with code `public_key_not_allowed`.

Keep your secret key private. Never expose it in client-side code, commit it to version control, or share it publicly.

## OpenAPI

A machine-readable OpenAPI 3.1 description of both APIs is published at [cap.so/openapi.json](/openapi.json). Import it into an API client, generate a typed client, or give it to an agent as tool definitions.

## Base URL

**REST API (secret key):**

```
https://cap.so/api/developer/v1
```

**SDK API (upload token):**

```
https://cap.so/api/developer/sdk/v1
```

If you are self-hosting Cap, replace `cap.so` with your custom domain.

## Error Handling

Every error is a JSON object with an `error` string, a stable `code`, a `hint` that says what to change, and a link to these docs. `message` holds the same text as `error`. Switch on `code`, not on the text.

```json
{
  "error": "Invalid secret key",
  "code": "invalid_secret_key",
  "message": "Invalid secret key",
  "hint": "Send Authorization: Bearer csk_... with a secret key from https://cap.so/dashboard/infra.",
  "docs": "https://cap.so/docs/api/rest-api"
}
```

A request body that fails validation returns `400` with the code `invalid_request` and an `issues` array that names each failing field:

```json
{
  "error": "Invalid request: maxResolutionTier: Invalid option: expected one of \"1080p\"|\"1440p\"|\"2160p\"",
  "code": "invalid_request",
  "message": "Invalid request: maxResolutionTier: Invalid option: expected one of \"1080p\"|\"1440p\"|\"2160p\"",
  "hint": "Fix the fields listed in issues, then send the request again.",
  "docs": "https://cap.so/docs/api/rest-api",
  "issues": [
    {
      "code": "invalid_value",
      "values": ["1080p", "1440p", "2160p"],
      "path": ["maxResolutionTier"],
      "message": "Invalid option: expected one of \"1080p\"|\"1440p\"|\"2160p\""
    }
  ]
}
```

A `402` from Create Upload or Complete Upload is the one exception to the shape: it has `error`, `code` and `message`, and carries the balance fields shown under [Create Upload](/docs/api/rest-api#create-upload) in place of `hint` and `docs`.

Send request bodies as JSON with the header `Content-Type: application/json`. Malformed JSON returns `400` with the code `invalid_json`, and a body sent with any other content type returns `415` with the code `unsupported_media_type`.

| Status Code | Description |
|-------------|-------------|
| `200` | Success |
| `400` | Bad request. The `code` says what was wrong, for example `invalid_request`, `invalid_json`, `invalid_limit` or `unknown_parameter` |
| `401` | Unauthorized. The API key or upload token is missing, invalid, revoked or expired |
| `402` | Payment required. The app is out of credit, its balance does not cover 7 days of storage, or it is below the minimum to start a transcript |
| `403` | Forbidden. On the SDK API, a public key was sent (`public_key_not_allowed`), the `Origin` differs from the upload token's `corsOrigin` (`origin_not_allowed`) or the body names another video (`video_mismatch`). Elsewhere, the account cannot use this feature yet |
| `404` | Not found. The video, transcript or upload does not exist (`video_not_found`, `transcript_not_found`, `upload_not_found`), or no route matches the path (`not_found`) |
| `405` | Method not allowed. The path exists but not with this method (`method_not_allowed`). The `Allow` header lists the methods it takes |
| `409` | Conflict with the current state, for example an upload that already completed. The `code` says which |
| `415` | Unsupported media type. The body was not sent as `application/json` |
| `429` | Too many requests. See [Rate Limits](/docs/api/rest-api#rate-limits) |
| `500` | Internal server error (`internal_error`). Retry with backoff |
| `503` | Transcription is temporarily unavailable. Retry later |

A `4xx` response will not succeed if the same request is sent again, with two exceptions that say to wait and repeat it: `429`, and `409` with the code `completion_in_progress`.

## Rate Limits

Each key and each upload token allows 60 requests per minute, counted across every endpoint. Playback URLs need no key and are not counted.

Every response carries three headers:

| Header | Meaning |
|--------|---------|
| `X-RateLimit-Limit` | Requests the key may make per minute |
| `X-RateLimit-Remaining` | Requests left in the current window |
| `X-RateLimit-Reset` | Seconds until the window resets |

Past the limit the API answers `429` with the code `rate_limited` and a `Retry-After` header in seconds. The count is kept by the server that answers, so `X-RateLimit-Remaining` can differ from one response to the next. Treat it as a guide, and treat a `429` with its `Retry-After` as the instruction.

Each upload token has its own count, separate from your secret key's and from every other upload. Each uploaded part spends one presign request from it.

## Pagination

List endpoints support pagination via query parameters:

| Parameter | Type | Default | Range | Description |
|-----------|------|---------|-------|-------------|
| `limit` | integer | 50 | 1 to 100 | Number of items to return |
| `offset` | integer | 0 | 0 and up | Number of items to skip |

Lists are strict about their query string. A `limit` or `offset` that is not a whole number in range returns `400` with the code `invalid_limit` or `invalid_offset`, and a query parameter the list does not know returns `400` with the code `unknown_parameter`. Parameter names are case-sensitive. Nothing is clamped or ignored, so a mistyped filter never returns an unfiltered list.

Video lists do not include pagination metadata. To paginate, increment `offset` by `limit` until the returned array has fewer items than `limit`. Transcript lists also return `pagination.hasMore`.

## REST API Endpoints

All REST API endpoints require a secret key (`csk_`) in the `Authorization` header.

### Create Upload

Create a video and an upload token for it. Call this from your server, then give the token to the browser that uploads the file.

```
POST /api/developer/v1/uploads
```

**Request body (JSON):**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | string | No | Video name, up to 255 characters (defaults to "Untitled") |
| `userId` | string | No | Your external user ID for filtering, up to 255 characters. Videos return it as `externalUserId` |
| `maxResolutionTier` | string | No | Highest resolution to encode: `1080p` (default), `1440p` or `2160p` |
| `metadata` | object | No | Your own JSON object to store with the video, under 8KB |
| `corsOrigin` | string | No | Exact origin of the page that uploads, such as `https://app.example.com`, with no path or trailing slash |
| `timeoutSeconds` | integer | No | How long the token works, in seconds from `60` to `86400`. Defaults to `3600` |

The body is optional. A request with no body creates an upload with the defaults.

**Example request:**

```bash
curl -X POST https://cap.so/api/developer/v1/uploads \
  -H "Authorization: Bearer csk_your_secret_key_here" \
  -H "Content-Type: application/json" \
  -d '{"name": "User Recording", "userId": "user_42", "corsOrigin": "https://app.example.com"}'
```

**Example response:**

```json
{
  "data": {
    "id": "abc123def456",
    "videoId": "abc123def456",
    "token": "cut_eyJ2IjoxLCJhcHAiOiIuLi4ifQ.Jm2c...",
    "expiresAt": "2026-03-10T15:30:00.000Z",
    "corsOrigin": "https://app.example.com",
    "status": "uploading",
    "uploadUrl": "https://cap.so/api/developer/sdk/v1/upload/multipart",
    "playbackId": "Zk3vQ9s2Lm8Rt1Xy7Bc4Df6G",
    "shareUrl": "https://cap.so/dev/Zk3vQ9s2Lm8Rt1Xy7Bc4Df6G",
    "embedUrl": "https://cap.so/dev/Zk3vQ9s2Lm8Rt1Xy7Bc4Df6G/embed"
  }
}
```

Each video takes one upload, so `id` equals `videoId`. `shareUrl` and `embedUrl` are a hosted player for the video. See [Share and Embed](/docs/api/rest-api#share-and-embed). To build your own player, see [Play a Video](/docs/api/rest-api#play-a-video).

The token is the only credential the [SDK API](/docs/api/rest-api#sdk-api-endpoints) accepts, and it is returned once:

- It uploads this video and no other.
- It works until `expiresAt`. The upload has to complete by then, so raise `timeoutSeconds` for large files on slow connections.
- It stops working when the upload completes or the video is deleted.

`corsOrigin` is a convenience for browser uploads. When it is set, the SDK API refuses a request whose `Origin` header is anything else. A script can send any `Origin` it likes, so the token is what protects the upload, not the origin. Leave `corsOrigin` out to upload from a server or a native app.

Creating an upload is free. It returns `402` if the app is out of credit or its balance does not cover 7 days of storage for what it already stores. The `402` body says how much is needed:

```json
{
  "error": "Insufficient credits",
  "code": "insufficient_credits",
  "message": "Uploading needs $0.20 of credit, enough for 7 days of storage for everything this app stores. The balance is $0.05, so add at least $0.15.",
  "standing": "active",
  "pausesAt": null,
  "balanceMicroCredits": 5000,
  "requiredMicroCredits": 19834,
  "shortfallMicroCredits": 14834
}
```

`code` is `insufficient_credits`, `out_of_credit` (the app is in `grace` or `paused`) or `no_account`.

```json
    "posterUrl": "https://cap.so/api/developer/playback/Zk3vQ9s2Lm8Rt1Xy7Bc4Df6G/poster.jpg"
  }
}
```

The `status` field moves from `uploading` to `processing` when the upload completes, then to `ready` or `errored`. `ready` is `true` when `status` is `ready`. When `status` is `errored`, `errorReason` says why.

Poll this endpoint every few seconds after completing an upload, and stop when `status` is `ready` or `errored`. Each call counts toward the key's 60 requests per minute.

A video is `ready` as soon as its first output can be played, so playback can start while the rest is still encoding. The playback URLs are `null` until then. `hlsUrl` is an adaptive HLS master playlist, `mp4Url` is a progressive MP4 and `posterUrl` is a poster image. They need no API key and can be loaded from any origin. [Play a Video](/docs/api/rest-api#play-a-video) shows how to use them, and [Delete Video](/docs/api/rest-api#delete-video) says when they stop working.

On a ready video, one of `hlsUrl` and `mp4Url` can still be `null` while that output finishes encoding. It is filled in later without the video leaving `ready`, and `renditions` is filled in together with `hlsUrl`. Play whichever URL is present.

`transcriptionStatus` is `null`. Uploaded videos are not transcribed automatically. To get text, send the file to [Transcripts](/docs/api/rest-api#transcripts).

### Delete Video

Delete a video. It is excluded from every query straight away, and its playback URLs stop answering new viewers within about a minute. Its files (the upload and every encoded output) are removed within about five minutes, and links that were already handed out stop working within about ten minutes of the delete. If the video was still being encoded when it was deleted, anything the encoder writes afterwards is removed within four hours.

Deleting a video this app already deleted returns success again, so the call is safe to repeat. An ID that never belonged to this app returns `404`.

```
DELETE /api/developer/v1/videos/:id
```

**Path parameters:**

| Parameter | Type | Description |
|-----------|------|-------------|
| `id` | string | The video ID |

**Example request:**

```bash
curl -X DELETE https://cap.so/api/developer/v1/videos/abc123def456 \
  -H "Authorization: Bearer csk_your_secret_key_here"
```

**Example response:**

```json
{
  "success": true
}
```

### Transcripts

Send an audio or video file and get text back. Transcription costs $0.10 per audio hour, billed by the second from the app's credit balance.

A transcript moves through these statuses: `uploading` (waiting for its file), `queued`, `processing`, then `complete` or `error`. Poll [Get Transcript](/docs/api/rest-api#get-transcript) every few seconds until the status is `complete` or `error`. Each key allows 60 requests per minute.

Creating or starting a transcript can be refused. The response carries a `code` and a `message`:

| Status | Code | Meaning |
|--------|------|---------|
| `402` | `out_of_credit` | The app is in `grace` or `paused` because a daily storage charge could not be paid. The message says how much to add |
| `402` | `insufficient_credits` | The available balance is under $0.01. The message says how much to add |
| `409` | `idempotency_conflict` | The `Idempotency-Key` was already used for a different request, or for a transcript that was deleted |
| `409` | `upload_not_found` | The file has not been uploaded yet |
| `503` | `speech_unavailable` | Transcription is temporarily unavailable. Retry later |

#### Transcribe a URL

```
POST /api/developer/v1/transcripts
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `url` | string | Yes | Public `http` or `https` URL of an audio or video file |
| `name` | string | No | Display name (defaults to the file name) |
| `language` | string | No | Two-letter code such as `en`, or `auto` (default) |
| `userId` | string | No | Your own user identifier, used to filter lists |
| `metadata` | object | No | Your own JSON object, under 8KB |

The URL must use the default port, must not contain credentials and must resolve to a public address. Redirects are followed up to five times and each hop is checked the same way. Files can be up to 2 GB, or 400 MB when the server does not send a `Content-Length`. Audio can be up to 4 hours long.

```bash
curl -X POST https://cap.so/api/developer/v1/transcripts \
  -H "Authorization: Bearer csk_your_secret_key_here" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: standup-2026-11-11" \
  -d '{"url": "https://example.com/standup.mp3"}'
```

```json
{
  "data": {
    "id": "8kq2m4x7n1p3v5w",
    "status": "queued",
    "name": "standup",
    "source": { "type": "url", "url": "https://example.com/standup.mp3" },
    "durationSeconds": null,
    "language": null,
    "wordCount": null,
    "costMicroCredits": 0,
    "costDollars": 0,
    "error": null,
    "userId": null,
    "metadata": null,
    "createdAt": "2026-11-11T10:30:00.000Z",
    "updatedAt": "2026-11-11T10:30:00.000Z",
    "completedAt": null
  }
}
```

Send an `Idempotency-Key` header (8 to 128 characters) so a retried request returns the same transcript instead of creating and billing a second one.

#### Transcribe a file

Uploading takes three calls: create the transcript, PUT the file, then start it.

```
POST /api/developer/v1/transcripts/uploads
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `contentLength` | integer | Yes | Exact file size in bytes, up to 2 GB |
| `fileName` | string | No | Original file name |
| `name`, `language`, `userId`, `metadata` | | No | Same as above |

The response is the transcript in the `uploading` status plus an `upload` object with a signed URL that is valid for one hour. Audio can be up to 4 hours long.

```bash
FILE=standup.m4a
SIZE=$(wc -c < "$FILE" | tr -d ' ')

CREATED=$(curl -s -X POST https://cap.so/api/developer/v1/transcripts/uploads \
  -H "Authorization: Bearer csk_your_secret_key_here" \
  -H "Content-Type: application/json" \
  -d "{\"fileName\": \"$FILE\", \"contentLength\": $SIZE}")

ID=$(echo "$CREATED" | jq -r .data.id)

curl -X PUT -T "$FILE" "$(echo "$CREATED" | jq -r .data.upload.url)"

curl -X POST "https://cap.so/api/developer/v1/transcripts/$ID/start" \
  -H "Authorization: Bearer csk_your_secret_key_here"
```

A single signed PUT is used instead of a multipart upload because it is one request any HTTP client can make. The upload must be exactly `contentLength` bytes. Starting a transcript twice is safe: the second call returns the transcript unchanged.

#### Transcript billing

- The price is $0.10 per audio hour, which is 10,000 micro-credits. Cap measures the audio length itself and bills it to the nearest second, with a minimum of one second. A length sent by the client is never used.
- Creating or starting a transcript needs an app in good standing and an available balance of at least 1,000 micro-credits ($0.01). Otherwise the API answers `402`, with `code` set to `out_of_credit` when the app is in `grace` or `paused` and `insufficient_credits` when the balance is under the minimum. The `message` says how much to add.
- Credits are taken once, when the transcript completes. A transcript that is retried internally is never charged twice.
- Audio with no speech is billed for its length and returns an empty transcript, because the audio was extracted and run through speech recognition.
- Never charged: a transcript that ends in `error` for any reason (a file that is not audio or video, a file with no audio track, a source that cannot be fetched or is too large, audio over 4 hours, not enough credit, a timeout, or a failure on our side), and a transcript deleted before it completes.
- Starting holds up to the cost of four hours ($0.40) until the audio is measured, then the hold drops to the real cost. The hold is placed before the file is downloaded or processed and nothing is charged for it. It is sized from the file: a file under 180 KB holds $0.01, a file of 7.2 MB or more holds the full $0.40, and a URL that does not report its size holds $0.40. The available balance is your balance minus those holds.
- If the available balance cannot cover the hold, the transcript ends with `insufficient_credits` before the file is downloaded or processed, and the error message says how much was needed. When other running transcripts hold the credit, it waits for them for up to 15 minutes first, so a batch started together runs through as holds are released.
- Credit held for a running transcript is left alone by the daily storage charge and is not counted when uploads are admitted. If the balance still cannot pay for a transcript in full when it finishes, the transcript ends with `insufficient_credits`, its text is discarded and nothing is charged. Top up and submit it again.
- Cap deletes the source file once the transcript finishes. The text and timings are kept until you delete the transcript.

Retrieve your app's credit balance, video totals, standing, what it needs to take an upload, what storage costs per day and the rates those costs are worked out from.

```bash
curl https://cap.so/api/developer/v1/usage \

```

**Example response:**

```json
{
  "data": {
    "balanceMicroCredits": 500000,
    "balanceDollars": "5.00",
    "totalVideos": 23,
    "uploadingVideos": 1,
    "totalDurationMinutes": 87.5,
    "standing": { "state": "active", "pausesAt": null },
    "upload": {
      "allowed": true,
      "reason": null,
      "requiredMicroCredits": 1736,
      "shortfallMicroCredits": 0,
      "message": null
    },

      "minutesByTier": { "1080p": 87.5, "1440p": 0, "2160p": 0 },

      "monthlyMicroCredits": 7438
    },

      "microCreditsPerDollar": 100000,

    }

```

Credits are tracked in micro-credits (1 dollar = 100,000 micro-credits).

**Totals.** `totalVideos` counts videos whose upload completed, and `totalDurationMinutes` is their combined length. `uploadingVideos` counts videos that were created and have not completed an upload.

**Rates.** `rates` holds the prices and rules the other fields are built from, so a client does not need to hard-code them: dollars to store 1,000 minutes for a 30 day month in each tier, dollars to transcribe one hour of audio, and the number of days of storage the balance must cover before an upload is accepted.

**What is billed.** Uploading and encoding are free. Stored video is charged once a day, for each video by its length and resolution tier, with a month counted as 30 days.

| Tier | Pixels (width times height) | Storage per 1,000 minutes per month |
|------|-----------------------------|-------------------------------------|
| `1080p` | up to 2,073,600 | $0.85 |
| `1440p` | up to 4,194,304 | $1.45 |
| `2160p` | above 4,194,304 | $2.80 |

A video is billed at the lower of two tiers: the tier its source falls in by pixel count, and the `maxResolutionTier` it was created with. A 3840 by 2160 upload created with the default `1080p` tier is encoded and billed at `1080p`. `storage.minutesByTier` groups minutes the same way.

**Uploading.** `upload.allowed` is true when the app is in good standing and its balance covers 7 days of storage for everything it stores. `upload.requiredMicroCredits` is that amount and `upload.shortfallMicroCredits` is how much to add.

**Standing.** `standing.state` is one of:

| State | Meaning |
|-------|---------|
| `active` | In good standing. |
| `grace` | A daily storage charge was more than the balance. The balance was taken to zero, uploads are blocked, and playback continues until `pausesAt`, 7 days after the app first fell short. |
| `paused` | Playback is paused until credits are added. Videos stay stored. |

Adding credits that cover one day of storage returns the app to `active` at once. Days it could not pay for are not charged afterwards.

## SDK API Endpoints

The SDK API uploads a video's file from a browser or app. Every endpoint takes the upload token from [Create Upload](/docs/api/rest-api#create-upload) in the `Authorization` header. The token already names the video, so `videoId` in a request body is optional, and a `videoId` that is not the token's returns `403` with code `video_mismatch`.

| Status | `code` | Meaning |
|--------|--------|---------|
| `401` | `invalid_upload_token` | The token is missing, malformed or altered |
| `401` | `upload_token_expired` | The token is past `expiresAt`. Create a new upload |
| `403` | `public_key_not_allowed` | A public key was sent. Public keys cannot create or upload videos |
| `403` | `origin_not_allowed` | The token has a `corsOrigin` and the `Origin` header is different |
| `403` | `video_mismatch` | The body names a video other than the token's |
| `404` | `video_not_found` | The token's video was deleted |

### Multipart Upload

After creating an upload, send its file in parts with the upload token:

1. Initiate the upload to get an `uploadId`.
2. Split the file into parts. Every part except the last must be at least 5 MB (5,242,880 bytes), and an upload can have up to 10,000 parts.
3. For each part, get a presigned URL, `PUT` the bytes to it and keep the `ETag` response header.
4. Complete the upload with the list of parts.

#### Initiate Upload

```
POST /api/developer/sdk/v1/upload/multipart/initiate
```

**Request body (JSON):**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `videoId` | string | No | The token's video ID |
| `contentType` | string | No | One of `video/mp4` (default), `video/webm`, `video/quicktime`, `video/x-matroska`, `video/avi` or `application/octet-stream`. Any other value is stored as `video/mp4` |

**Example request:**

```bash
curl -X POST https://cap.so/api/developer/sdk/v1/upload/multipart/initiate \
  -H "Authorization: Bearer cut_your_upload_token_here" \
  -H "Content-Type: application/json" \
  -d '{"contentType": "video/mp4"}'
```

**Example response:**

```json
{
  "uploadId": "multipart-upload-id"
}
```

#### Get Presigned Part URL

Get a presigned URL to upload a single part.

```
POST /api/developer/sdk/v1/upload/multipart/presign-part
```

**Request body (JSON):**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `videoId` | string | No | The token's video ID |
| `uploadId` | string | Yes | The upload ID from the initiate step |
| `partNumber` | integer | Yes | Part number, from 1 to 10,000 |

**Example request:**

```bash
curl -X POST https://cap.so/api/developer/sdk/v1/upload/multipart/presign-part \
  -H "Authorization: Bearer cut_your_upload_token_here" \
  -H "Content-Type: application/json" \
  -d '{"uploadId": "multipart-upload-id", "partNumber": 1}'
```

**Example response:**

```json
{
  "presignedUrl": "https://..."
}
```

The URL is valid for one hour. Upload the part by sending a `PUT` request to it with the bytes as the body and no extra headers:

```bash
curl -X PUT -T part-1.bin -D - "$PRESIGNED_URL"
```

Save the `ETag` header from the response for the completion step. Send it as it was returned. The quotes around it are optional.

#### Complete Upload

Finalize the upload after all parts have been uploaded.

```
POST /api/developer/sdk/v1/upload/multipart/complete
```

**Request body (JSON):**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `videoId` | string | No | The token's video ID |
| `uploadId` | string | Yes | The upload ID |
| `parts` | array | Yes | Every uploaded part, at least one. A part left out of the list is left out of the video |
| `parts[].partNumber` | integer | Yes | The part number, from 1 to 10,000 |
| `parts[].etag` | string | Yes | The ETag returned when the part was uploaded |
| `parts[].size` | number | Yes | The size of the part in bytes |
| `durationInSecs` | number | Yes | Positive video duration in seconds. It is replaced by the measured duration once processing has read the file |
| `width` | number | No | Video width in pixels |
| `height` | number | No | Video height in pixels |
| `fps` | number | No | Video frame rate |

**Example request:**

```bash
curl -X POST https://cap.so/api/developer/sdk/v1/upload/multipart/complete \
  -H "Authorization: Bearer cut_your_upload_token_here" \
  -H "Content-Type: application/json" \
  -d '{
    "uploadId": "multipart-upload-id",
    "parts": [
      { "partNumber": 1, "etag": "\"9b2cf535f27731c974343645a3985328\"", "size": 5242880 },
      { "partNumber": 2, "etag": "\"3858f62230ac3c915f300c664312c63f\"", "size": 1048576 }
    ],
    "durationInSecs": 12.5
  }'
```

**Example response:**

```json
{
  "success": true
}
```

Completing an upload charges nothing. The video's stored `duration` is the greater of the submitted duration and a minimum based on the part sizes reported by storage, bounded by what the uploaded bytes could hold and capped at four hours. Storage for the video is billed daily from then on, by its length and resolution tier.

A mistake in the request returns one of these:

| Status | `code` | Meaning | What to do |
|--------|--------|---------|------------|
| `400` | `parts_required` | `parts` is empty. | Send the `partNumber` and ETag of every part you uploaded. |
| `400` | `parts_mismatch` | A listed part is missing from storage, is listed twice or has a different ETag. | Upload the missing part again, then send each part once with the ETag its `PUT` returned. |
| `400` | `part_too_small` | A part other than the last is under 5 MB. | Initiate again and upload the file in larger parts. |
| `404` | `upload_not_found` | No open upload matches the `uploadId`. It was aborted or the ID is wrong. | Initiate again and upload the parts again. |

The balance must cover 7 days of storage for everything the app stores including this video. If it does not, complete returns `402` with the same body as [Create Upload](/docs/api/rest-api#create-upload), and the upload stays open so the same request succeeds after a top-up. The one exception is when several uploads finish at once and together exceed the balance: the `402` then carries `"fileRemoved": true`, the file that was just assembled has been removed, and it must be uploaded again once credit is added.

Each video accepts one completed upload, and its token is used up with it. Once the upload completes, initiate, presign-part and abort return `409` with the code `upload_already_completed`, and repeating complete returns `{ "success": true }` without doing anything.

Complete can itself return `409` with a `code`:

| `code` | Meaning | What to do |
|--------|---------|------------|
| `completion_in_progress` | Another request is completing this upload right now, for example your own earlier request whose response was lost. | Wait a few seconds and send the same complete request again. Do not abort the upload or delete the video. |
| `upload_removed` | The upload sat unrecorded for more than a day and was removed. | Create a new upload and send the file again. |

Abort also returns `409` with `completion_in_progress` while a completion holds the video. Every SDK API endpoint returns `404` with the code `video_not_found` once the video is deleted. To upload a new file, create a new upload.

#### Abort Upload

```
POST /api/developer/sdk/v1/upload/multipart/abort
```

**Request body (JSON):**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `videoId` | string | No | The token's video ID |
| `uploadId` | string | Yes | The upload ID to abort |

**Example response:**

```json
{
  "success": true
}
```

## Play a Video

A ready video has three playback URLs, and a hosted player for when you do not want to build one.

| Field | Use it for | What it is |
|-------|------------|------------|
| `hlsUrl` | Playback | An adaptive HLS master playlist. The player picks a rendition for the viewer's connection and switches as it changes |
| `mp4Url` | The fallback, and downloads | One progressive MP4 file |
| `posterUrl` | The image shown before playback starts | A JPEG frame from the video |
| `shareUrl`, `embedUrl` | No player to build | A hosted player page and an iframe embed. See [Share and Embed](/docs/api/rest-api#share-and-embed) |

The playback URLs need no API key and answer any origin, so there is no CORS setup to do.

### Play with hls.js

Safari plays HLS by itself. Every other browser needs [hls.js](https://github.com/video-dev/hls.js). This page plays the video everywhere, with the MP4 as the fallback:

```html
<video id="player" controls playsinline poster="POSTER_URL"></video>
<script src="https://cdn.jsdelivr.net/npm/hls.js@1"></script>
<script>
  const video = document.getElementById("player");
  const hlsUrl = "HLS_URL";
  const mp4Url = "MP4_URL";
  let hls = null;

  function fallBackToMp4() {
    const position = video.currentTime;
    const wasPlaying = !video.paused;
    if (hls) {
      hls.destroy();
      hls = null;
    }
    if (!mp4Url) return;
    video.src = mp4Url;
    video.currentTime = position;
    if (wasPlaying) video.play();
  }

  if (hlsUrl && window.Hls && Hls.isSupported()) {
    hls = new Hls({ capLevelToPlayerSize: true });
    hls.loadSource(hlsUrl);
    hls.attachMedia(video);
    hls.on(Hls.Events.ERROR, (event, data) => {
      if (data.fatal) fallBackToMp4();
    });
  } else if (hlsUrl && video.canPlayType("application/vnd.apple.mpegurl")) {
    video.src = hlsUrl;
    video.addEventListener("error", fallBackToMp4, { once: true });
  } else if (mp4Url) {
    video.src = mp4Url;
  }
</script>
```

Replace `HLS_URL`, `MP4_URL` and `POSTER_URL` with the video's `hlsUrl`, `mp4Url` and `posterUrl`. A ready video can still have `hlsUrl` or `mp4Url` set to `null` while that output finishes encoding. Pass `null` for that one and the page plays the other.

- hls.js runs wherever the browser supports Media Source Extensions. A browser without them that plays HLS itself gets the playlist directly, and anything else gets the MP4.
- Keep the checks in that order. `canPlayType` is not a test for Safari by itself, because Chrome answers it for HLS too.
- If hls.js hits an error it cannot recover from, the page switches to the MP4 at the same position and keeps playing.
- If the browser's own HLS player fails, the page loads the MP4 in its place. A viewer who had already pressed play may have to press it again.
- `capLevelToPlayerSize` stops hls.js from loading a rendition larger than the player. Without it, a small player on a fast connection climbs to the largest rendition.
- There is no start level to set. The master playlist lists a rendition that starts quickly first, and players begin with the first one listed.

### Play in Safari

A page that only has to work in Safari needs no script:

```html
<video src="HLS_URL" poster="POSTER_URL" controls playsinline></video>
```

If the video's `hlsUrl` is still `null`, use its `mp4Url` as the `src`.

### Stable URLs, Redirects and Caching

- `hlsUrl`, `mp4Url` and `posterUrl` are stable. Store them and reuse them for as long as the video exists.
- `mp4Url` and `posterUrl` answer with a `302` redirect to a signed URL on the media host, `v.cap.so`. Browsers and video players follow it. Do not store the URL you were redirected to.
- The playlists behind `hlsUrl` list signed media URLs on the same host. A signed URL works for 12 hours. A player left paused for longer than that has to load the playlist again before it can fetch more of the video.
- Playback answers are cached for 60 seconds by browsers and shared caches, so a change such as a delete or a top-up can take up to a minute to show.

The page above recovers from expired media URLs by itself, by switching to the MP4. To stay on HLS, add this function to the same script. It loads the playlist again and returns to the same position:

```js
function reloadPlaylist() {
  if (!hls) return;
  const position = video.currentTime;
  hls.once(Hls.Events.MANIFEST_PARSED, () => {
    video.currentTime = position;
  });
  hls.loadSource(hlsUrl);
}
```

Call it when a viewer comes back to a player that loaded its playlist more than 12 hours ago, then call `video.play()`. It does nothing once the page has switched to the MP4. In Safari, set `video.src` to the `hlsUrl` again and then set `video.currentTime`.

### Content Security Policy

A site with a Content Security Policy has to allow two hosts: `https://cap.so`, which serves the playback URLs, and `https://v.cap.so`, which serves the media they point to. For the hls.js page above:

```
connect-src https://cap.so https://v.cap.so;
media-src blob: https://cap.so https://v.cap.so;
img-src https://cap.so https://v.cap.so;
worker-src blob:;
```

| Directive | Why |
|-----------|-----|
| `connect-src` | hls.js fetches the playlists from `cap.so` and the media from `v.cap.so` |
| `media-src` | hls.js feeds the video element through a `blob:` URL. The two hosts cover the MP4 fallback and HLS in Safari |
| `img-src` | The poster is loaded from `cap.so` and redirects to `v.cap.so`, so both are needed |
| `worker-src` | hls.js does its work in a worker created from a `blob:` URL. Without this it still plays, on the main thread, and the browser logs a violation |

The scripts need allowing too. Add the origin you load hls.js from to `script-src`. The page above also starts the player from an inline script, which a `script-src` without `'unsafe-inline'` blocks, so the video never gets a source. Move that script into a file your policy allows, or give the tag a nonce or a hash that the policy lists.

A page that plays HLS in Safari without hls.js needs only `media-src` and `img-src` with the two hosts. To use `embedUrl` in an iframe, allow `frame-src https://cap.so`.

If you self-host Cap, use your own web origin and the host your playback URLs redirect to.

### Bitrates

`renditions[].bitrate` is the average bitrate of a rendition. The `BANDWIDTH` in the master playlist is its peak, and players choose a rendition by the peak. The peak can be more than twice the average, most of all for screen recordings, so a viewer whose connection matches a rendition's `bitrate` can be given the one below it.

### The MP4

`mp4Url` is a single file, at most the dimensions of the largest rendition. It is not part of the adaptive ladder, so every viewer gets the same file whatever their connection.

When the upload is already H.264 and fits the tier, Cap can keep its video as uploaded instead of encoding it again, and the MP4 then has the bitrate of the upload. On the `2160p` tier that can be a source-quality 4K file, which is large. Use `hlsUrl` for playback on that tier, and keep `mp4Url` for downloads and as the last fallback.

### When Playback Stops

- **The app is out of credit.** When an app is `paused`, every playback URL answers `402` with a plain text reason: `Playback is paused because the account that hosts this video is out of credit.` Neither hls.js nor the MP4 can load, so the video element fires an `error` event. Listen for it to show your own message. Playback returns within a minute of credits being added. An app in `grace` still plays. See [Get Usage](/docs/api/rest-api#get-usage) for the standings.
- **The video was deleted.** The playback URLs answer `404` with the plain text `Not found`. [Delete Video](/docs/api/rest-api#delete-video) gives the timings for new viewers and for links that were already handed out. A deleted video and an ID that never existed answer the same way.
- **An output is not encoded yet.** A URL that is `null` in the API has nothing behind it yet and would answer `404`. Wait for the field to be filled in.

## Share and Embed

Every video has a hosted player, returned as `shareUrl` and `embedUrl` when you create an upload and when you get or list a video. Both are built from the video's `playbackId`, need no API key or sign-in, set no cookies and are kept out of search engines.

- `shareUrl` is a page with the player and the video's name. Send it to a viewer as a link.
- `embedUrl` is the player alone, filling whatever frame you give it. Any site can load it in an iframe:

```html
<iframe
  src="https://cap.so/dev/Zk3vQ9s2Lm8Rt1Xy7Bc4Df6G/embed"
  title="Product Demo"
  style="width: 100%; aspect-ratio: 16 / 9; border: 0"
  allow="fullscreen; picture-in-picture"
  allowfullscreen
></iframe>
```

Set the iframe's `aspect-ratio` from the video's `width` and `height`. The links work as soon as the video is created: until it is `ready` the page says the video is processing and switches to the player by itself, and if processing failed it shows `errorReason`. A deleted video returns `404`, and a video in an app whose playback is paused says so.

The full video object returned by list and get endpoints:

| Field | Type | Description |

| `appId` | string | The developer app that owns this video |

## Best Practices

- **Use secret keys server-side only.** The `csk_` key should never appear in client-side code. Create each upload on your server and send only its `cut_` upload token to the browser.
- **Poll video status after upload.** After completing a multipart upload, poll `GET /videos/:id/status` every few seconds until `status` is `ready` or `errored`, then play `hlsUrl` when it is present and `mp4Url` otherwise. See [Play a Video](/docs/api/rest-api#play-a-video).
- **Switch on `code`.** Every error carries a stable `code`. The `error` text can change.
- **Watch the rate limit headers.** Each key and each upload token allows 60 requests per minute. Slow down as `X-RateLimit-Remaining` nears zero, and wait for `Retry-After` seconds after a `429`.
- **Store your keys securely.** Use environment variables or a secrets manager.
- **Check who is uploading before you create an upload.** Your server decides who gets a token, so authenticate the user first and set `userId` to tie the video to them.
- **Monitor your credit balance.** Use the usage endpoint to track the balance, `standing` and `upload.allowed`, and top up from your app's Billing page in Cap Infra. Auto top-up on that page adds credits from a saved card when the balance runs low.
- **Paginate large result sets.** Use `limit` and `offset` to retrieve videos in batches. When the returned array length is less than `limit`, you have reached the end.
