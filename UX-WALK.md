# Worm

Worm is an independent AGPLv3 fork of [Cap](https://github.com/CapSoftware/Cap). It extends the shipping GPUI desktop app with Worm Mode, a native walk recording mode. Upstream copyrights and the MIT and third-party exceptions in [LICENSE](LICENSE) remain in place.

Worm was previously named Cap UX. The README explains what stayed the same so it installs over that app.

## Record a walk

1. Select **Worm Mode** in the menu bar, main recorder or mode picker. A fresh Chrome window opens at your configured start page and is selected for recording. The menu bar switches to the Worm mark. Onboarding introduces the same mode alongside Instant, Studio and Screenshot.
2. Enter a topic and, when enabled, confirm speaker names in the recorder. The recorder warns if the selected transcription provider has no saved key. The new browser window stays selected while you configure the walk, and **Start Recording** stays visible at the bottom. **New walk window** opens another fresh window. Every Chrome window the walk opened closes when the walk ends, when you leave Worm Mode, or when its start fails or is superseded, and Restart keeps it open. Your own Chrome windows are never touched. You can switch to any display, window, area or camera with the existing capture-source controls.
3. Choose a display, window, area or camera, then use the existing camera, microphone and system-audio controls. Start recording normally.
4. Open **Walk notes & chapters** from the recording bar. Add an observation or give the next chapter a title. Notes save immediately. Cap's existing Stop, Pause, Resume, Restart and Delete controls own the capture lifecycle.
5. Stop to save the Cap project and prepare the walk. The native review window shows progress, notes, the report and files. **Edit a copy** opens an independent editing project in the existing editor.

For a meeting plus a live demo, select the demo **Window**, enable **Record System Audio**, and select your **Microphone**. On macOS, computer audio uses its own ScreenCaptureKit stream, independent of the video window: a call in another app is included without recording that app's video. System Audio includes other apps and notifications; it is not a participant-only call feed. Microphone remains a separate source on the same recording timeline. Headphones help keep remote speech out of the microphone. ElevenLabs uses the audio that reaches the recording; diarization does not guarantee participant names.

To check this routing on a Mac, open a silent synthetic page in its own window, then run `python3 scripts/test-independent-audio.py --cap /path/to/cap-cli --window <native-window-id> --output /tmp/unique-audio-check`. This records only that window with the microphone disabled and plays a known tone and synthetic meeting speech through a different process. The test checks the saved audio for that tone. Repeat with `--mode studio` and with `--audio off` for the off control. It requires Screen Recording access and an audible output device; it never uploads the result.

Worm Mode uses Cap's Studio recording pipeline and native controls. The notes window is created before capture and explicitly excluded. A unique local bootstrap title identifies the new owned Chrome window before navigation; unrelated personal Chrome windows are never selected or instrumented. Its browser collector starts before the start-page navigation, recording semantic clicks, bounded visible context, console warnings/errors, page exceptions and request-completion metadata. Failed JSON responses retain redacted error codes, messages, details and hints. Request bodies, auth headers, cookies, form values and raw automation-trace archives are excluded from reports.

The owned browser context uses the configured local `authFile` to retain sign-ins; it is separate from your personal Chrome profile. You may need to sign in there once. Browser creation does not start video recording. First-load context before Start is saved separately in `browser-preroll.jsonl`, outside the video timeline. Captured events and native notes use Cap's elapsed clock, excluding pauses; browser annotation screenshots stop while paused. First-frame alignment remains approximate. Events from separate popup windows are excluded; tabs in the selected window remain observable.

On macOS, window video uses ScreenCaptureKit's desktop-independent window filter, including after a capture-stream restart. It captures the selected window instead of cropping the display, so overlapping applications stay out of the video. A missing or excluded selected window fails without falling back to display capture. Display and area recording retain their existing behavior.

After confirmed recording finalization, the app snapshots the project into the walk folder before restoring normal completion UI. For an unedited recording, source microphone and computer audio are aligned to each capture segment, including silent spans and calibrated offsets, and chapter transcription starts alongside video export. The saved transcript survives an export failure; reprocessing reuses it. Edited timelines and unsupported audio layouts keep the rendered-audio path so captions match the exported video. Transcription still uses the selected provider and can be disabled. The processor reuses the verified session video for a chapter covering the full recording; other chapter boundaries retain accurate video cuts. Screenshots, timelines and optional briefs finish after video is available. `processing.json` records separate audio, transcript and video readiness with stage timestamps. If an export ends early, chapter captions are bounded to its duration and the complete early transcript is retained as `transcript-source.srt`. The original recording stays in Worm's library. A failed export retains source media and notes; reprocessing reuses the saved snapshot. Restart and Delete discard the current Cap capture through its existing controls and retain an aborted notes journal without processing it as a completed walk.

Saved journals are remembered across app launches. Settings → Recordings includes a **Worm Mode** filter, **View notes** and **Copy agent prompt** for each associated recording. Saved notes can open the report/files, reprocess an interrupted preparation, or explicitly open a Claude session in cmux. The existing Shortcuts page offers **Open Worm Mode** and **Open walk notes**. Walk folders retain the report, journal, browser evidence and media; handoff prompts describe the evidence actually available and treat recorded content as observations rather than instructions.

## Recover important evidence while recording

New walks checkpoint the native journal and unsent note draft, complete click/error-log lines, and complete AAC fragments locally about every ten seconds. Writes synchronize files and directory entries before advancing the durable cursor. A timer is a target, not a crash-loss guarantee: unreadable or incomplete media tails remain outside saved coverage, and disk errors appear in the walk status. Video recording does not wait for transcription or network acknowledgements. Source checkpoints consume additional local disk space and are retained with the walk.

**Transcribe while recording** in Transcription sends roughly five-minute source chunks to the selected ElevenLabs or AssemblyAI provider, then a short tail after stop. This uses your existing provider key and can incur provider charges during capture. None makes no requests; Descript and unsupported live media use the after-stop path. Ogg has no live fragment support. A short closed segment can produce a smaller chunk. Each source/chunk keeps its own clock and speaker identity. Transcribers number voices per request and return no voiceprint, so voices cannot be matched across chunks. A walk with one configured speaker and only microphone speech, with under 2% of its words outside each chunk's busiest voice, names that person throughout. Any other walk keeps separate labels per source/chunk, and its report says two labels can be the same person. Capture pauses are already represented by the recorder's media clocks. Global alignment remains provisional until display spans and final track offsets are available.

Saved successful jobs, including silent results, are reused at final preparation. Pending, failed or ambiguous coverage stays visibly partial and does not trigger a full automatic paid resubmission. A lost provider response may already have been billed; it is retained as ambiguous. A job that never sent a request, such as one that ran with no saved key, is failed rather than ambiguous and carries no charge risk: it runs again without a manual retry when the key appears or on **Resume evidence sync**. To explicitly allow another paid attempt, stop the existing worker and run `node <bundle>/checkpoint-worker.mjs /absolute/path/native-walk.json --retry-job <job-sha256>`. The same ownership lock prevents concurrent workers, and a job permits at most three manual retries. Provider requests have a real two-minute cancellation deadline. Stop drains bounded work for up to roughly two and a half minutes and retains remaining jobs/outbox entries for **Resume evidence sync** in saved notes. If the drain itself fails, saved notes show the error and that step. Resume does not cancel a running saved job at the deadline. When healthy stop-tail jobs finish, the existing processor refreshes a partial report automatically, reusing the saved video and transcript cache. Refresh waits at most roughly two and a half minutes for another processor; a timeout retains the partial report and an immutable refresh diagnostic. Failed or ambiguous transcription stays partial and requires an explicit retry. Unsupported edited timelines retain source-qualified results rather than inventing final caption alignment. A source that cannot do live transcription automatically uses stop-time transcription once the worker has sealed its final checkpoint and relinquished ownership, provided no live provider job was ever prepared or submitted. Its saved results are reused on subsequent Reprocess. After evidence sync finishes, **Transcribe full audio again (provider charges)** in saved notes explicitly requests a rendered-audio transcription for unsupported/Ogg capture or missing coverage. It archives previous captions and supersedes unsubmitted live jobs. Ordinary Reprocess then uses verified results from that request; it does not silently start another paid request. At most three explicit full requests are permitted per walk. Resume evidence sync to back up the new full transcript.

**Back up new walks privately** in Settings → Sharing is a separate, initially off choice. Enabling normal sharing does not enable it. Private backup uploads original source speech, transcript chunks, native notes/drafts and sanitized click/error logs to your configured server using its existing owner credential. It creates no public link. Recording source audio can contain other people and app notifications; later editor mutes, cuts or deletes do not remove earlier original backup content. Turning backup off pauses pending uploads; changing the server also pauses the old outbox. Restoring the same server and a valid rotated credential resumes it. A walk pins its original server and retention choice.

Progress separates saved journal clocks, event byte cursors, per-source saved audio, server-acknowledged audio and transcribed ranges. A journal clock does not establish audio or event completeness. The UI reports unsupported/missing sources and errors; `checkpoint-status.json` contains the separate cursors and `checkpoints/` retains immutable objects, descriptors, receipts and jobs.

Use **Recover private backup** in saved notes or Sharing settings, choose an authenticated backup, then a parent folder for a new recovered copy. Restore verifies all object hashes, sizes, source identities and fragment contiguity before issuing a recovery receipt. Recorded absolute paths are replaced with owned paths inside the new folder. An interrupted report can show notes, speech, audio and click/error logs without a finalized MP4; it remains marked interrupted. Partial downloads remain in their separate folder without a ready receipt and never overwrite the original recording.

Restored audio retains every source placement, even when separate intervals contain identical bytes. The receipt and audio controls identify each source time range; a single verified audio file can serve multiple placements. Exact repeated references are deduplicated.

Recovery uses the existing cloud Worker's owner-authenticated `/api/v1/recovery` API and existing R2 bucket. It must be deployed separately with the updated server source before backup will work; there is no deployment during a desktop build. Registration fixes retention at 1–30 days (default seven), and the API denies access after expiry. The existing bucket's 31-day lifecycle eventually deletes objects physically. Owner-authenticated DELETE writes a tombstone before paginated cleanup; repeat while the API returns cleanup pending. Recovery has no public viewer capability, and it does not back up video. Network loss or a computer crash before remote acknowledgement can still lose the unacknowledged tail.

For a retained outbox, `node <bundle>/checkpoint-worker.mjs /absolute/path/native-walk.json` resumes local jobs and private uploads through the bundled `cap-cli` credential bridge. `cap-cli recovery status --json` exposes nonsecret settings; `cap-cli recovery request --server-origin https://your-server --method DELETE --resource /api/v1/recovery/<recording-uuid> --json` deletes a private backup. Never place a credential in these arguments or request files.

Ordinary Reprocess preserves confirmed chapter speaker maps, participant lists and attribution notes only when capture, chapter bounds and transcript provenance still match. Confirmed maps take precedence over Meet inference. Changed source or fresh full transcription archives the old metadata and captions in `speaker-attribution-history/` and marks the report for speaker reconfirmation.

## Prepare an editable demo

The bundled `cap-demo` companion skill can prepare an existing recording for optional local FilmCraft and EffectCraft tools. Run `node <skilldir>/cap-demo.mjs prepare /path/to/native-walk.json --out /path/to/new-demo`, review the generated `edit.json`, then run `node <skilldir>/cap-demo.mjs render /path/to/new-demo`. A `.cap` project or video is also accepted; videos can reuse an SRT with `--captions`. `doctor` checks the optional tools. The skill is installed with the existing `zworm agents install` workflow.

This first bridge copies the source, keeps its hashes, maps explicit cuts and existing caption cues onto one output clock, and optionally inserts an editable EffectCraft title card. Each attempt creates a separate FilmCraft project and local HTML review under `renders/`; failures retain their draft files. It makes no model or cloud calls. Source bundles can move and render again; native editor projects may need media relinking after moving. Preproduction UI, word-level cuts and arbitrary graphics layouts are follow-ups. See [the companion skill](apps/cli/skill/cap-demo/SKILL.md) for commands and the tested tool versions.

## Settings and providers

General contains your name, start page, speaker defaults, handoff preference, chapter briefs and product source folder. Recordings contains the walk output folder. Transcription contains ElevenLabs Scribe, AssemblyAI, Descript and None, plus language, glossary and screen-name preferences. Ordinary editor captions retain their existing local models.

Native settings share `~/.config/ux-walk/config.json` with the engine and CLI. Invalid or unsupported changes are refused; unrelated preferences are preserved. Provider secrets stay in login Keychain items, including configured custom item names. Secure key entry sends secrets to the security utility over stdin, never command arguments, JSON or logs.

Other capture sources retain Cap's normal flexibility. If the chosen window/display/area does not match an owned walk browser, its report explicitly marks browser evidence unavailable. Old walks remain video/manual-note recordings; missing telemetry cannot be recovered retroactively. Interrupted collectors report partial coverage. Browser-visible query failures do not provide server-side SQL traces. The separate CLI's trace preference remains preserved in shared settings.

Automatic walk windows require Google Chrome. The walkthrough processor requires FFmpeg. Optional briefs require the configured Claude CLI. Opening an agent workspace requires Claude and cmux; it is never automatic. Cloud transcription requires a provider key and sends audio to the selected provider. Worm Mode does not automatically publish recordings.

## Build and preview

Use the existing Cap GPUI setup and packaging pipeline. Install pinned engine dependencies with `npm ci --ignore-scripts --prefix vendor/ux-walk`, then run `node scripts/bundle-ux-walk.mjs /path/to/Worm.app` after packaging. The bundle contains Node, the pinned engine and a fork-owned native lifecycle adapter in `Contents/Resources/ux-walk`. No separate UX Walk application is required.

The bundler also compiles `apps/desktop-gpui/ux-walk/walk-chrome-launcher.c` into the engine's `bin`. Walk Chrome starts through it so that macOS treats Chrome as responsible for itself. Otherwise macOS holds the app responsible and may say it was prevented from modifying apps. If the launcher is missing or fails, the collector logs a line to stderr and starts Chrome normally. Recording does not need App Management.

The bundler copies the Node that runs it, so run it with a self-contained Node 22, such as the nodejs.org build or `actions/setup-node`. It refuses any other version, a Node linked to libraries outside `/usr/lib` and `/System`, such as a Homebrew one, and a Node that cannot run `--version` from the app.

The bundler signs nested code inside out (each bundled framework and library, then Node), then signs the app with `apps/desktop-gpui/packaging/macos/Entitlements.plist`, and its last step verifies the app's seal. Packaging without a signing identity leaves the frameworks unsigned, and this order covers them without a manual `codesign`. Changing any file inside the app after that breaks the seal, and macOS then reports the app as damaged. After touching the bundle, rerun `node scripts/bundle-ux-walk.mjs` with the same `CAP_UX_SIGNING_IDENTITY` so it signs and verifies again.

Checkpoint work and full transcription share an OS-held ownership guard; ordinary video/report processing has a separate guard and can overlap live transcription. Guard identity uses the resolved walk directory and filesystem identity, so aliases share ownership. PID files are advisory for current guards; known-live legacy owners still block a mixed-version attempt. Crash metadata is archived, unknown files are retained, and the OS guard is released only after owned metadata cleanup. The loopback-only socket accepts no application protocol; an unrelated port collision fails closed rather than starting a second writer.

The public engine snapshot contains selected source files, license, contract tests and per-file hashes in `SOURCE.json`. Refresh it with `scripts/sync-ux-walk.mjs` from a reviewed canonical revision; do not edit the snapshot directly. The lifecycle adapter is maintained under `apps/desktop-gpui/ux-walk`.

The **ux-walk native checks** workflow checks the desktop and CLI, runs scoped tests and packages an isolated macOS 15+ preview. Preview artifacts include the app, source revision, engine provenance, licenses and checksum. The app uses the Worm name and icon. Previews have a separate bundle identifier and per-revision temporary data, logs, recordings and UX Walk config. They claim no recording file association or URL scheme and do not copy your official Cap profile.

A signed public installer and fork-owned binary update feed are not available yet. The default `ux-walk` Cargo feature blocks official Cap installers from overwriting the fork. Do not distribute a build with `--no-default-features`, which restores the official updater.

CI previews use ad-hoc signatures. Their signing identity changes with the binary, so a permission entry from an older preview may remain enabled while the new app sees access denied. Use the same existing local signing identity for successive local builds with `CAP_UX_SIGNING_IDENTITY="your signing identity" node scripts/bundle-ux-walk.mjs "/path/to/Worm.app"`. This signs the preview; it does not grant permissions. In macOS Privacy & Security, refresh only the Worm entries with the exact installed app, then relaunch it. [Apple's screen recording guide](https://support.apple.com/guide/mac-help/control-access-screen-system-audio-recording-mchld6aa7d23/mac) and [accessibility guide](https://support.apple.com/en-mo/guide/mac-help/mh43185/mac) describe those controls.

## Upstream and distribution

Upstream changes arrive as reviewed update pull requests and are built before release. Keep customizations in fork-owned modules and extend Cap's recording and editor paths. Worm uses its own application identity, library and account state.

Commercial use and paid distribution are possible under the applicable open source licenses, with corresponding source and required notices available to recipients. Upstream cloud subscriptions, infrastructure and service terms remain separate. This fork does not deploy a cloud service or implement production session analytics.
